# AuditSphere — Business lifecycle diagram crosswalk

**Status: CURRENT execution assessment; not architecture or acceptance approval.**

The owner-supplied **STEAuditSphere Complete Practice Management Lifecycle** diagram is a business journey, not a complete technical architecture. This crosswalk records observed owners and gaps without replacing current requirements, approved ADRs, task dependencies or acceptance evidence. Source and test results belong in [status.json](status.json). No application tests were executed for this document.

The governing technical model remains [current architecture](../architecture/auditsphere-architecture-current-architecture.md): Angular → authenticated same-origin ASP.NET API → static Application capabilities → Domain and EF/PostgreSQL, plus isolated durable Workers and scoped provider adapters. File presence below establishes implementation location, not that every acceptance criterion passes. [Code map](../architecture/auditsphere-architecture-code-map.md) and [ADR register](../architecture/adr/auditsphere-architecture-index-adr-register-current.md) retain detailed ownership and decisions.

## Lower-layer ownership and cross-cutting controls

- **Identity/access:** `Domain/Security/Users.cs`, Infrastructure `Persistence/AuditSphereDbContext.Security.cs`; API trusted cookie/anti-CSRF/session freshness; Application authorization remains authoritative on direct reads, commands, retry and export. Navigation availability is only a bounded presentation hint.
- **Commercial/client/engagement:** `Domain/Practice/Crm.cs`, `Commercial.cs`, `ClientConversion.cs`, `Domain/Engagements/Engagements.cs`, `EngagementCreation.cs`; corresponding `AuditSphereDbContext.Practice.cs`, `AuditSphereDbContext.ClientConversions.cs`, `AuditSphereDbContext.EngagementCreations.cs` mappings retain client/service identities and receipts.
- **Audit/release:** `Domain/Audit/`, `Domain/Completion/`, `Domain/Records/`; corresponding Audit/Completion and records configuration preserve revisions, human decisions, frozen snapshots and manifest hashes.
- **Three financial domains:** `Domain/Practice/FirmLedger.cs` and `Billing.cs` remain firm finance; `Domain/Accounting/ClientAccounting.cs` with client-accounting mappings owns client books; `AuditSphereDbContext.Consolidation.cs` owns group snapshots/results. Shared UI does not merge ledgers.
- **Shared client portal:** UI `portal/home.ts`, `documents.ts`, `finance.ts`, `activity.ts`; `UiEndpoints.Portal.cs`; APP `Documents/ClientPortalReviewQuery.cs`, `ClientPortalFinanceQuery.cs`, `ClientPortalActivityQuery.cs`. Exact client/engagement grants precede paging and document download. Bounded overflow must not appear as a complete archive. Client communication does not imply a general-purpose mailbox integration.
- **Shared work/finance:** UI `practice/work-queue.ts`, `time.ts`, `finance/invoice.ts`; workflow/time/finance API owners; APP `Practice/WorkflowTaskQueueQuery.cs`, `PracticeTimeService.cs`, `BillingService.cs`. Task applicability is distinct from professional procedure applicability. [UX register](auditsphere-execution-ux-workflow-tasks-current.md) retains unresolved context selection, route filters, package-review discovery in My Work, next actions, template preparation and exact-task handoffs.
- **Durable work/integrations:** `AuditSphereOps.Worker/Program.cs` composes isolated executable groups. Existing render/build, mail, PBC and client-site handlers retain command identity, retry/reconciliation and exact-resource boundaries. SharePoint adapters live under Infrastructure `Providers/`; authoritative issued custody remains ADR-0009's store. Actual permissions, provider outcomes and unknown external results require observed evidence, not simulation labels.

## Prioritized gaps and acceptance leaves

1. **Shared queue/context usability — engineering:** continue U02/U03/U04/U07/U08/U11/U12/U14 in the existing UX register, preserving capability hints, current authorization, exact task identity and unknown-outcome recovery. Verify interrupted navigation, refresh/revocation and old/off-page tasks, not only an empty queue.
2. **Truthful archive/exit handoff — engineering plus policy boundary:** immediately distinguish the existing archive marker from offboarding in user guidance. Design a scoped read-only open-work/billing/access readiness view using existing owners before any new exit command. A true exit operation requires explicit retained review, exact scope, immutable evidence and separately authorized access changes; do not add financial write-offs or destructive cleanup.
3. **Group delivery/archive — multi-layer engineering:** the [module contract](../task_breakdown/modules/auditsphere-r2r-module-26-consolidation-contract.md) explicitly ends at approved run/readback and declares M37/M38 integration. A coherent packet needs immutable export bytes bound to approved current run/component snapshots, independent release decision, authorized download and durable archive of those same bytes. Do not label U/V complete from existing entity-package or audit archive code.
4. **Current-source evidence — verification:** execute focused affected checks locally, then exact-source CI and complete release suites only in CI. Renewals, roll-forward, package receipt, role revocation and cross-route stale-source handoffs require connected acceptance. Historical passes and the architecture image cannot satisfy them.
5. **Qualified/external leaves:** T003 methodology/golden outcomes, firm certificate/legal acceptance, live Entra/selected-site/provider delivery, independent checkpoint/custody, restore/capacity and real-tenant acceptance remain qualified or external gates. They block dependent acceptance, not independent code repair.

## Diagram interpretation constraints

The arrows are journey prompts, not a command order or authorization rule. P→Q does not authorize delivery merely because a period is closed; S→U does not bypass component currentness; K→L does not copy prior approvals; W→X does not make archive revoke access. The image does not specify consistency/transaction boundaries, revision fencing, idempotency, exact-source lineage, provider isolation, secret custody, disaster recovery or observability; the technical architecture and retained acceptance registers supply those requirements. Purview and third-party eSignature remain excluded; certificate signing is governed separately by ADR-0016.
