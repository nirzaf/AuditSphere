# Development tenant and local verification

**Status: HISTORICAL development record.** The pinned source/commands below predate Blazor retirement. Read current repository AGENTS.md and the [client-tenant CLI guide](auditsphere-m365-runbook-client-tenant-current.md) for operative instructions. Do not recreate the retired host or run complete local regressions from this dated record.

This guide records the **Development** setup used to exercise AuditSphereOps with a Microsoft Entra developer tenant and synthetic PostgreSQL clients. It is an operator procedure, not a production deployment recipe or acceptance record. Use the [Production Configuration Guide](auditsphere-deployment-guide-production-current.md) and [Production Entra ID Configuration](auditsphere-m365-runbook-client-tenant-current.md) for production requirements. The [execution ledger](https://github.com/nirzaf/AuditSphere/blob/7469313/docs/execution/status.json) holds the observed checks and remaining gates; source and evidence revisions are identified there.

The primary local presentation is the Angular `AuditSphereOps.Ui` frontend served by `AuditSphereOps.Api`: build it (`npm --prefix src/AuditSphereOps.Ui run build`), run the Api host against the local PostgreSQL database, and use the same-origin staff workbench at `/ui/app`, the client portal at `/ui/portal`, and initial setup at `/ui/setup/microsoft365`. The step-by-step screens below were written for the legacy `AuditSphereOps.Web` Blazor rollback host (routes without the `/ui` prefix); they reuse the same Application services and the `/auth` and `/health` endpoints, so treat each bare route there as the rollback equivalent of the `/ui/...` primary route.

## Prerequisites and boundary

1. On the macOS development host, use the repository's .NET 10 SDK and PostgreSQL 18 on loopback port `5433`. Run commands from the AuditSphere repository root in a terminal. The local database setup and restore commands are in the [repository README](https://github.com/nirzaf/AuditSphere/blob/3767640/README.md); confirm the target is a disposable development database before applying migrations. A failed PostgreSQL connection must be repaired before starting the Web host.
2. Use an approved **non-production** Entra tenant, an organizational-account web registration, and its exact local callback URI, `http://localhost:<PORT>/signin-oidc`. The port must match the actual local Web listener. Use the same tenant ID and app client ID in the private Development configuration. The current Web host reads `Identity:ClientSecret`; put the approved credential in the project's .NET user-secrets store or another private runtime source, never in `appsettings.json`, Git, Wiki, screenshots, or shell history. If the callback fails, compare the listener URL, registration redirect URI, and `Identity:CallbackPath` exactly.
3. Keep `ExternalEffects:Enabled=false`. The current Development profile permits local simulation adapters and a separately configured read-only selected-site test; it does not execute live document writes, mail, records, or release providers. The separate production Web registration, credentials, Data Protection profile, and selected-resource worker grants are described in the production pages. Do not copy a development registration or local identity setting into production.

The source defaults for the local database, simulation fence, and release gates are in [Web `appsettings.json`](https://github.com/nirzaf/AuditSphere/blob/3767640/src/AuditSphereOps.Web/appsettings.json). The Web project declares a stable [user-secrets ID](https://github.com/nirzaf/AuditSphere/blob/3767640/src/AuditSphereOps.Web/AuditSphereOps.Web.csproj). This guide intentionally omits actual tenant, app, user, installation, client, and secret values.

## Bind the first local administrator

1. An authorized installation owner configures the exact `Setup:FirmId`, `Setup:InstallationId`, `Setup:InitialAdministratorTenantId`, `Setup:InitialAdministratorObjectId`, and `Setup:BootstrapProofHash` privately. The proof itself stays out of configuration and logs. Follow [one-time owner onboarding](auditsphere-m365-runbook-client-tenant-current.md#one-time-owner-onboarding) for the single-use proof and fresh sign-in sequence.
2. Start the Development Web host against the intended local database and visit `/health/live` and `/health/ready`. Readiness means the local database and migration checks passed; it says nothing about tenant provider access. If the protected app shows a setup or sign-in error, inspect the local host logs without copying tokens or proof values into shared diagnostics.
3. Sign in as the nominated administrator, complete the private proof step at `/setup/microsoft365`, and complete the fresh sign-in requested after local binding. Open `/app/administration` and verify the exact local firm-wide Administrator grant, current Development mode, and fenced external effects. The Microsoft 365 setup draft remains separate from Graph consent or selected-site verification.
4. For later setup work, open `/app/administration/microsoft365` while signed in as that bound administrator and select **Continue setup with this account**. The existing draft opens without asking for the proof again; an empty tenant field takes the authenticated tenant ID. Enter the approved working-site URL separately. The advanced section holds resource IDs, optional capabilities and folder templates; saving the draft still does not verify SharePoint access. If continuation is denied, check the current local Administrator grant and exact signed-in identity rather than reusing the initial proof. This flow is implemented at [source revision `dd5425d`](https://github.com/nirzaf/AuditSphere/blob/dd5425d/src/AuditSphereOps.Web/Components/Pages/Microsoft365Setup.razor).

## Check selected-site read access in Development

1. **Administrator-only:** In the non-production Entra app registration, confirm the existing Microsoft Graph `Sites.Selected` application permission and the intended site-specific grant. Register only the public half of a separate runtime certificate under **Certificates & secrets**; keep its private key in an approved private runtime location outside Git and the Wiki. A certificate listing or tenant consent alone does not prove access to a particular site.
2. In the private Development Web configuration (for example the project's .NET user-secrets store), set `SelectedSite:TenantId`, `SelectedSite:ClientId`, `SelectedSite:CredentialReference`, `SelectedSite:CertificatePath`, and `SelectedSite:PrivateKeyPath` for the separately approved runtime certificate. The credential reference must match the prepared connection revision. Supply the actual private paths and identifiers only through the private configuration source, then restart the Web host. If the certificate is absent, the test fails closed; do not copy the key into the repository or Wiki.
3. In `/app/administration/microsoft365`, save the approved HTTPS working-site URL and stable site, document-library drive, and root-folder IDs returned by a bounded Graph read. The **Client Content** library is the current Development read-test target. With a prepared connection, the firm-wide Administrator can click **Test selected site connection**. The [read-only implementation at `7469313`](https://github.com/nirzaf/AuditSphere/blob/7469313/src/AuditSphereOps.Infrastructure/Providers/Microsoft365SelectedResourceTestService.cs) checks the current local grant, then the exact stored tenant/site/library/root with a `Sites.Selected` application token. A pass appears on screen; it does not record consent or selected-resource evidence, create content, or activate the workspace. If it fails, check the runtime certificate, site-specific grant and saved IDs without adding tenant-wide Graph scopes.
4. Separately verify that a synthetic unrelated site is denied with the same runtime identity, and keep that test result in a private evidence store. The setup button does not perform this negative check. The Worker still has no live PBC provider composition.

The [execution ledger at `7469313`](https://github.com/nirzaf/AuditSphere/blob/7469313/docs/execution/status.json) records a live non-production certificate-backed read, unrelated-site denial, and administrator button result. Those results do not demonstrate upload, exact-version retrieval, retry reconciliation, or production acceptance. Do not mark a connection active from read-only evidence.

## Create narrowly scoped synthetic fixtures

1. Prepare two fictional local clients through an authorized Development-only fixture procedure. Record their client IDs in a private test run record. Do not use real client names, files, financial data, or production grants. An Entra account by itself cannot create a local AuditSphere client or grant.
2. In Entra, use distinct enabled **test** accounts for staff and each client. Read their immutable tenant and object IDs from the approved roster or a verified sign-in. Do not infer identity from email, display name, directory job title, or administrator status. Password entry and MFA belong to the account holder.
3. As the bound local AuditSphere administrator, open `/app/administration` → **Verified roster role administration**. Enter the exact tenant ID, object ID, email, display name, identity kind (`Staff` or `Client`), and evidence source from the approved roster. Choose **Bind user**. Do this for each intended existing Entra user before they sign in; the administrator does not need to log in as each user. Binding creates no application role by itself. A tenant administrator who lacks the local AuditSphere administrator grant must first complete the approved application bootstrap or be granted that local role by another authorized administrator.
4. For the staff fixture, select `Staff` and **Selected client**, then enter only that synthetic client's ID. For each client fixture, select `ClientUser` and **Selected client**, using its own client ID. Review the selected local user, role, scope, and client before choosing **Save access and create invitation**. The page defaults to `Staff` and **Firm-wide** on a new selection; never accept those defaults for a narrow fixture. The resulting invitation intent is local evidence, not proof that mail was delivered.
5. Read back the grant list. Each test account should have only its intended client scope and no firm-wide or sibling-client grant. The administrator can configure every user's local binding, role, scope, invitation intent and later revocation from this account; individual Microsoft sign-ins are needed only to use the application and verify the live identity flow. The account holder completes any Microsoft password, MFA or Authenticator registration. If an ID is rejected, check the client exists in the current firm and that the UI finished binding the input; do not retry the final save blindly or change to firm-wide to make it pass. Use the audited administration service to change or revoke access; direct database role edits are not the operator path.

The UI and server-side checks are in [Administration.razor](https://github.com/nirzaf/AuditSphere/blob/3767640/src/AuditSphereOps.Web/Components/Pages/Administration.razor) and [RoleAdministrationService](https://github.com/nirzaf/AuditSphere/blob/3767640/src/AuditSphereOps.Application/Security/RoleAdministrationService.cs). The [execution ledger](https://github.com/nirzaf/AuditSphere/blob/b672e75/docs/execution/status.json) records local staff and two client fixture sign-ins after the administrator assigned their roles without signing in as them. The two client portals had no assigned content, so cross-client data denial remains unverified; a grant or a sign-in alone is not that test.

## Verify sign-in and isolation

1. In a fresh browser session, open `/auth/sign-in?selectAccount=true` to ask Microsoft for account selection. If Microsoft resumes an existing administrator session, use `/auth/sign-in?reauthenticate=true` for a fresh sign-in prompt. These options do not grant roles. Complete password and MFA in Microsoft's browser flow; never share them in a test report.
2. A mapped staff fixture should reach `/app` and see only its granted synthetic client. A mapped client fixture should reach `/portal` and see only its own assigned client data. Test direct sibling-client URLs, search/export paths, and protected administrator routes as well as the landing page. A successful portfolio or portal screenshot alone does not prove every command or download boundary.
3. An authenticated but unbound user should see **Access not assigned**, not a server error or a privileged page. Check wrong-tenant, disabled-local-user, revoked-grant, changed-UPN, and stale-session behavior separately with approved test identities. Record which were actually run; do not mark unperformed negative fixtures complete.

## Local capacity observations

The repository includes a synthetic maximum-input trial-balance import test (20,000 balanced CSV rows) and a simulated durable PBC transfer test (one 8 MiB chunk). Run the focused tests with PostgreSQL available, then use the [standard verification sequence](https://github.com/nirzaf/AuditSphere/blob/master/AGENTS.md) for the Release build, full suite, and EF model check. The exact observed timings, source commit, and limits are in the [execution ledger](https://github.com/nirzaf/AuditSphere/blob/3767640/docs/execution/status.json); do not treat these samples as a latency service level, concurrent-session result, live Graph throughput, or production sizing approval. The documented 15-staff and related volume scenarios are provisional workload inputs until a pilot owner approves actual concurrency and data sizes.

## What remains external

The local setup screen can test read access to the saved selected site, library and root. That result alone does not verify write access, grant isolation or production readiness. A separate Development read probe observed an unrelated-site denial; provider upload/readback, production secret custody, cross-store recovery, live observability, independent review, and real-tenant acceptance remain open. Keep those gates in the execution ledger. The signed-in developer account's access to Entra administration does not establish an Azure subscription or authorize production infrastructure. Purview and eSignature provider integrations are outside the approved product scope.
